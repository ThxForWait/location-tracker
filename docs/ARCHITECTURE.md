# Albion Location Tracker

Трекер переходов между локациями в **Albion Online** для построения общей карты **Дорог Авалона** (Roads of Avalon).

Дороги Авалона — сеть зон `TNL-*`, связанных порталами, которые появляются и исчезают. Карту этой сети невозможно составить заранее, её можно только собирать по наблюдениям игроков. Проект решает эту задачу автоматически:

1. **Трекер** (этот репозиторий, Go, Windows) пассивно читает сетевой трафик игры, определяет, из какой локации в какую перешёл игрок, и отправляет переход на сервер.
2. **Сервер** ([`location-tracker-web`](https://github.com/ThxForWait/location-tracker-web), Django) принимает переходы от многих игроков, проверяет их правдоподобие, учитывает доверие к игрокам и рисует общую карту живых порталов.

Трекер **только читает** трафик: он ничего не отправляет в игру, не меняет клиент и не читает память процесса.

## Как это работает

```
 Albion Online ──UDP 5056──►  [capture]  ──payload──►  [photon]  ──ответы 41/2──►  [tracker]
   (клиент игры)              все сетевые             разбор протокола         определение перехода
                              интерфейсы              Photon                   и тип ребра
                                                                                    │
                                                                                    ▼
 [сервер] ◄──HTTPS, Bearer-токен──  [api] ◄──очередь в памяти──  [Sender]  ◄────────┘
   проверки, доверие,                                            отдельная горутина
   общая карта
```

1. Игрок переходит из зоны в зону. Сервер игры присылает клиенту ответ на операцию **41** (переход начался, ID новой зоны), затем экран загрузки и ответ на операцию **2** (вход в зону, окончательный ID).
2. Трекер видит эти пакеты, сравнивает новую зону с текущей и классифицирует переход: дорога Авалона, постоянная связь открытого мира или что-то, что на карту не попадает (город, данж, хайдаут).
3. Переход ставится в очередь и уходит на сервер в фоне, не задерживая разбор трафика.
4. Сервер проверяет данные, объединяет отчёты разных игроков об одном портале и показывает ребро на карте.

## Архитектура клиента

```
main.go         — связывает модули, флаги командной строки
capture/        — захват пакетов со всех сетевых интерфейсов
photon/         — разбор протокола Photon (Protocol18)
tracker/        — логика переходов и фоновая отправка
api/            — клиент HTTP API v1 сервера
auth/           — получение и хранение токена устройства
config/         — константы и база зон
data/zones.json — справочник зон игры (встроен в exe)
dump/           — запись трафика для исследования (ветка traffic-dump)
```

### 1. `capture/` — захват пакетов

Используются [gopacket](https://github.com/google/gopacket) и драйвер [Npcap](https://npcap.com). Фильтр BPF `udp and port 5056` пропускает только трафик игрового сервера.

**Захват со всех интерфейсов.** Раньше трекер выбирал один «лучший» интерфейс, и при включённом VPN (Cloudflare WARP, WireGuard, OpenVPN) пакеты игры уходили мимо него. Теперь:

- `capture.Start` открывает **все** интерфейсы, на каждый — отдельная горутина;
- раз в 10 секунд список интерфейсов перечитывается: VPN-адаптеры появляются только в момент подключения, пропавшие интерфейсы закрываются;
- чтение с таймаутом 500 мс вместо `BlockForever`, иначе закрытие handle на Windows может зависнуть.

**Выбор активного интерфейса** (`capture/selector.go`). Читается только один интерфейс:

- активным становится первый, с которого пришёл трафик игры;
- копии тех же пакетов на других интерфейсах (мосты Hyper-V, split-tunnel VPN) отбрасываются, иначе сборка фрагментов собьётся;
- если активный интерфейс молчит дольше 3 секунд, а трафик пошёл по другому, трекер переключается на него. Так обрабатывается включение VPN посреди игры;
- при переключении парсер Photon создаётся заново, чтобы недособранные фрагменты со старого интерфейса не смешались с новыми.

**Разные канальные уровни.** Ethernet, loopback Npcap и «сырой IP» VPN-адаптеров разбираются по `LinkType`. Wintun и TAP через Npcap отдают `DLT_RAW = 12`, которого gopacket не знает, поэтому при неудаче пакет разбирается как голый IPv4/IPv6.

### 2. `photon/` — разбор протокола Photon

Albion работает на движке **Photon** (Exit Games). Парсер написан с нуля:

- заголовок пакета, команды (reliable, unreliable, fragment, disconnect);
- **сборка фрагментов** больших сообщений: повторные фрагменты отбрасываются по смещению, число одновременно собираемых сообщений ограничено (64), чтобы не расти по памяти при потерях;
- десериализация **Protocol18**: сжатые целые (varint, zigzag), строки, массивы с типом элементов, словари, хэш-таблицы, вложенные операции и события, кастомные типы;
- **настоящий код операции или события Albion** лежит не в заголовке Photon (там только 0–255), а в параметре **253** (операции) или **252** (события);
- время в протоколе Albion передаётся в **.NET ticks** (100 нс с 0001-01-01) в UTC.

### 3. `tracker/` — определение переходов

**Определение перехода** (`tracker/tracker.go`):

| Сообщение | Когда приходит | Где ID зоны |
|---|---|---|
| ответ на операцию **41** | в начале перехода, до экрана загрузки | параметр 0 |
| ответ на операцию **2** | после загрузки, вход в зону | параметр 8 |

Источник истины — только ответ **2**. ID из 41 нужен для сверки: при расхождении пишется предупреждение, но переход всё равно учитывается. Повтор той же зоны игнорируется. Первая зона после запуска (переход из `unknown`) не отправляется.

**Классификация зон** по полю `type` из `data/zones.json`:

| Категория | Типы зон | Что делаем |
|---|---|---|
| **дорога** (`ZoneRoad`) | `TUNNEL_*` (зоны `TNL-*`) | участвует в динамических рёбрах |
| **город** (`ZoneCity`) | королевские города с банками и рынками, их порталы в чёрной зоне, Карлеон, Брисилиен, логово антиквара | **никогда не отправляется** |
| **статичная** (`ZoneStatic`) | `OPENPVP_*`, `PASSAGE_*`, перекрёстки, Rest, Smuggler's Den | участвует в статичных рёбрах |
| **инстанс** (`ZoneInstance`) | данжи, острова, хайдауты, арены, Мгла, неизвестные ID | не отправляется |

**Что уходит на сервер:**

- хотя бы один конец — дорога → **динамическое ребро** (`DynamicEdge`, у него есть время жизни);
- оба конца статичные → **статичное ребро** (`StaticEdge`, постоянная связь открытого мира);
- город, инстанс или старт с `unknown` → только в локальный лог `location_history.log`.

Классификация **одинакова** в клиенте (`config/zones.go`) и на сервере (`albiontrackermap/zones.py`), файлы `zones.json` в обоих проектах совпадают.

**Фоновая отправка** (`tracker/sender.go`). HTTP-запрос может занимать секунды, поэтому трекер не ходит в сеть сам, а кладёт переход в очередь `Sender`:

- очередь только в памяти, 256 элементов; `Enqueue` никогда не блокирует разбор пакетов, при переполнении переход отбрасывается;
- **повторы** только при сетевых ошибках, 5xx и 429: 2, 4, 8, 16, затем по 30 секунд, или дольше, если сервер прислал `Retry-After`;
- **422 и 409** означают, что данные не прошли проверку сервера: переход отбрасывается без повторов;
- **401 и 403** (токен отозван, бан) и **426** (трекер устарел) останавливают отправку до перезапуска, причина пишется в лог один раз;
- переход старше **5 минут** выбрасывается: сервер всё равно его отвергнет;
- на Ctrl+C даётся 3 секунды на досылку очереди.

### 4. `api/` — клиент HTTP API v1

- база адреса `…/api/v1`; пути `/edges/dynamic`, `/edges/static`, `/me`, `/device/start`, `/device/poll`;
- заголовки `Authorization: Bearer atm_…` и `X-Client-Version`;
- ошибки сервера приходят как `{"detail": "...", "code": "..."}` и превращаются в `APIError{Status, Code, Detail, RetryAfter}`;
- классификация ошибок: `IsRetryable`, `IsAuthError`, `IsOutdated`, `IsPending`;
- время всегда в UTC, формат `2026-10-12T14:33:07Z`.

### 5. `auth/` — токен устройства

Каждая установка трекера получает свой токен через **вход в браузере** (device flow, как у GitHub CLI):

1. трекер запрашивает у сервера одноразовый код и открывает страницу `/link/?code=K7F-2QX`;
2. человек входит на сайт через **Discord** и подтверждает код;
3. трекер раз в 3 секунды опрашивает сервер и получает токен.

Токены хранятся в `%APPDATA%\AlbionTracker\config.json` **отдельно для каждого адреса API**, чтобы локальный и боевой серверы не мешали друг другу. При старте токен проверяется через `GET /me`. Если он отозван, вход запускается заново; если сервер недоступен, трекер работает с сохранённым токеном.

### 6. `dump/` — запись трафика для исследования

Режим `-dump файл.jsonl` (ветка `traffic-dump`) записывает **каждое** сообщение Photon одной строкой JSON. В записи:

- тип сообщения, код Photon и настоящий код Albion;
- текущая зона, размер, неразобранный остаток (`rest > 0` значит, что десериализатор «съехал»);
- все параметры с сохранением типов: `int64`, вложенные массивы и словари, байтовые блоки целиком;
- сырые байты сообщения в hex.

Строки, введённые в консоли, записываются как заметки (`mark`), например «открыл карту, портал в TNL-123 8ч 32м». В этом режиме отправка на сервер выключена.

## Сервер

Репозиторий [`location-tracker-web`](https://github.com/ThxForWait/location-tracker-web): Django 6.1, Python 3.12, зависимости через **uv**.

| Часть | Технология |
|---|---|
| API | Django Ninja (Pydantic-схемы, документация `/api/v1/docs`) |
| Вход на сайт | django-allauth, только через Discord (scope `identify`) |
| База | SQLite (планируется переезд) |
| Лимиты запросов | встроенные throttles Ninja, счётчики в `DatabaseCache` |
| Карта | vis-network, данные через `json_script` |

**Модель данных:**

- **`Edge`** — динамическое ребро как **агрегат**: одно живое ребро на пару зон. Повторный отчёт о том же портале добавляет подтверждение, а не создаёт дубль. Поля: `confirmations`, `reporters_count`, `last_seen`, `expires_at`, `status` (`unconfirmed` / `confirmed` / `disputed`). Пара зон нормализуется: проход в обратную сторону — то же ребро.
- **`StaticEdge`** — постоянное ребро, флаг «эталон» (`is_reference`).
- **`Player`** — игрок, привязанный к Discord: доверие `trust`, флаги `is_trusted`, `banned`.
- **`DeviceToken`** — токен устройства; в базе хранится только SHA-256.
- **`DeviceLoginCode`** — одноразовый код входа через браузер, живёт 10 минут.
- **`EdgeReport`** — каждый присланный переход как есть: кто, откуда, IP, итог проверки (`accepted` / `suspicious` / `rejected`) и причины.

**Страницы сайта:**

- `/map/` — общая карта живых порталов;
- `/accounts/login/` — вход через Discord;
- `/link/` — подтверждение кода трекера;
- `/account/devices/` — список подключённых трекеров с отключением;
- `/admin/` — бан, «доверенный», сброс доверия, отзыв токенов, отметка эталонных рёбер.

**Карта.** Все карты рисуются одним шаблоном, выборка рёбер вынесена в `maps.py`. Общая карта показывает живые рёбра; неподтверждённые рисуются пунктиром, спорные скрыты, рёбра с городами не показываются. Узлы разложены по полосам: открытый мир слева, дороги Авалона в центре, чёрная зона справа. У каждого ребра таймер до истечения.

## API v1

| Метод | Путь | Авторизация | Назначение |
|---|---|---|---|
| GET | `/api/v1/health` | — | проверка доступности |
| GET | `/api/v1/me` | токен | кому принадлежит токен |
| POST | `/api/v1/device/start` | — | начать вход через браузер |
| POST | `/api/v1/device/poll` | — | получить токен после подтверждения |
| POST | `/api/v1/edges/dynamic` | токен | переход через портал Авалона |
| POST | `/api/v1/edges/static` | токен | постоянный переход открытого мира |

Пример тела `POST /edges/dynamic`:

```json
{
  "source_id": "TNL-342",
  "target_id": "3356",
  "created_at": "2026-10-16T02:11:20Z",
  "expires_at": "2026-10-16T04:11:20Z"
}
```

Ответ: `201` — новое ребро, `200` — подтверждение существующего:

```json
{"edge_id": 7, "source_id": "3356", "target_id": "TNL-342", "created": true,
 "status": "unconfirmed", "confirmations": 1, "expires_at": "2026-10-16T04:11:20Z"}
```

**Коды ошибок:**

| Код | `code` | Значение |
|---|---|---|
| 401 | `unauthorized` | нет токена или он отозван |
| 403 | `banned` | игрок заблокирован |
| 409 | `not_in_reference` | статичного ребра нет в эталоне |
| 410 | `code_expired`, `code_used` | код входа истёк или уже использован |
| 422 | `invalid_payload`, `unknown_zone`, `same_zone`, `wrong_kind`, `city_zone`, `created_in_future`, `too_old`, `invalid_lifetime` | данные не прошли проверку |
| 426 | `client_outdated` | трекер старее минимальной версии |
| 428 | `authorization_pending` | вход ещё не подтверждён |
| 429 | `rate_limited` | слишком много запросов, см. `Retry-After` |

## Защита данных от подделки

Клиент работает на чужом компьютере, поэтому доказать, что запрос отправила именно настоящая сборка трекера, нельзя: любой вшитый секрет можно извлечь. Защита строится на четырёх уровнях: **кто** прислал, **сколько**, **правдоподобно ли** и **подтверждают ли другие**.

**Уровень 1 — личность.**

- вход только через Discord;
- аккаунты моложе 30 дней токен не получают (возраст вычисляется из Discord ID — snowflake);
- у каждого устройства свой токен, который можно отозвать.

**Уровень 2 — лимиты.**

- 20 отчётов в минуту и 300 в час на токен;
- отдельные лимиты по IP на вход через браузер.

**Уровень 3 — правдоподобие** (`validation.py`).

Отказ (отчёт сохраняется как отклонённый):

- неизвестная зона, одинаковые концы, тип ребра не соответствует зонам, переход с городом;
- `created_at` из будущего больше чем на 30 секунд или старше 5 минут;
- время жизни портала больше 4 часов;
- статичное ребро вне эталона, когда граф законсервирован.

Пометка «подозрительный» (отчёт принимается):

- **разрыв пути:** прошлый переход игрока закончился не там, откуда начинается новый;
- меньше 5 секунд между переходами;
- у зоны дорог больше 8 живых выходов.

**Уровень 4 — доверие и подтверждение** (`trust.py`).

- ребро подтверждено, если о нём сообщили **два независимых игрока** (разные аккаунты и разные IP) или один надёжный;
- доверие: +1 за ребро, которое подтвердил другой игрок; −0.5 за подозрительный отчёт; −1 за отклонённый;
- игрок с доверием ниже −5 в **карантине**: его отчёты сохраняются, но ребро, о котором сообщали только игроки в карантине, становится спорным и на карте не показывается.

Все пороги вынесены в настройки сервера (`TRACKER_*`).

## Сборка и запуск

**Требования:** Go 1.27+, Windows, установленный [Npcap](https://npcap.com). Если в Npcap включено «только для администраторов», трекер нужно запускать от администратора.

```bash
go build -ldflags "-X location-tracker/config.Version=1.0.0" -o tracker.exe .
```

| Команда | Что делает |
|---|---|
| `tracker.exe` | работа с боевым сервером (**без флагов данные идут на боевой сервер!**) |
| `tracker.exe -debug` | работа с локальным сервером `http://127.0.0.1:8000/api/v1` |
| `tracker.exe -api <url>` | свой адрес API (база `…/api/v1`) |
| `tracker.exe -login` | заново подключить трекер к аккаунту |
| `tracker.exe -token atm_…` | использовать токен из флага, не сохраняя его |
| `tracker.exe -list` | список сетевых интерфейсов |
| `tracker.exe -iface <имя>` | слушать только один интерфейс |
| `tracker.exe -zones <файл>` | подменить встроенный `zones.json` |
| `tracker.exe -dump файл.jsonl` | записать трафик для исследования (ветка `traffic-dump`) |

При первом запуске трекер откроет браузер для входа через Discord.

**Локальный сервер** (в папке `location-tracker-web`):

```bash
uv sync
uv run python manage.py migrate
uv run python manage.py createcachetable
uv run python manage.py runserver 8000
```

Сайт открывать по `http://127.0.0.1:8000`, а не `localhost`: так прописан redirect приложения Discord. Ключи Discord и секреты лежат в `.env`, шаблон — `.env.example`.

## Настройки

Клиент (`config/config.go`):

| Константа | Значение | Смысл |
|---|---|---|
| `BPFFilter` | `udp and port 5056` | фильтр захвата |
| `InterfaceSwitchAfter` | 3 с | тишина, после которой переключаемся на другой интерфейс |
| `InterfaceRescanInterval` | 10 с | как часто искать новые интерфейсы |
| `PortalLifetime` | 2 ч | время жизни портала, отправляемое на сервер (временное значение) |
| `SendQueueSize` | 256 | размер очереди отправки |
| `SendMaxAge` | 5 мин | старше — переход не отправляется |
| `SendShutdownGrace` | 3 с | досылка при выходе |
| `Version` | `dev` | задаётся при сборке через `-ldflags` |

Сервер: все пороги проверок, лимитов и доверия — в `config/settings.py` с префиксом `TRACKER_`, секреты — в `.env`.

## Ограничения и известные проблемы

- **Время жизни портала неизвестно.** Игра показывает таймер порталов на карте, но в открытом трафике его нет. Исследование дампа показало, что данные о порталах зоны (назначение и время) приходят **зашифрованными** сообщениями Photon, по одному на портал. Ключ шифрования согласуется через обмен Диффи — Хеллмана и из перехваченного трафика не восстанавливается. Расшифровка потребовала бы читать память клиента игры, а это обход защиты и нарушение правил игры, поэтому так не делаем. Пока отправляется фиксированное время жизни 2 часа.
- **Адрес API зашит в exe.** При смене домена или хостинга все выпущенные трекеры перестанут работать. Перед раздачей игрокам нужен свой постоянный домен. Перенаправления со старого адреса не помогут: Go при переходе на другой домен отбрасывает заголовок `Authorization`.
- **SmartScreen и антивирусы.** Неподписанный exe вызывает предупреждение SmartScreen. Упаковщики (UPX) и обфускаторы не используются, они добавляют ложные срабатывания. Npcap нельзя встраивать в свой установщик без OEM-лицензии: пользователь ставит его сам.
- **WAN Miniport** открываются захватом без ошибок и просто молчат.
- **Ложный «разрыв пути».** Если игрок перезапустил трекер посреди сессии, его следующий переход может быть помечен как подозрительный. Окно проверки — 30 минут.

## Планы

- **Подсчёт порталов в зоне.** Зашифрованные сообщения нельзя прочитать, но можно посчитать. Сервер узнает реальное число выходов зоны, а карта покажет, где ещё не разведано.
- **Оценка времени жизни** портала по наблюдениям: первое и последнее подтверждение, исчезновение порталов из зоны.
- **Личная карта игрока** (всё, что он открыл сам, без фильтров доверия) и **пулы** — закрытые группы игроков со своей картой, публичные или приватные.
- **Общая карта в прошлом:** как выглядел Авалон в выбранный момент.
- **Свой домен** и адрес API из внешнего файла, ссылка на обновление при ответе 426.
- **Переезд сервера** на другую базу данных и хостинг.
